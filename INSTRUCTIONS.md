# Neon + Better Auth — what's already done, and what's left for you

Everything code-side has been implemented and verified (`tsc --noEmit` passes, and a
production build traces cleanly through every new file — see "What was verified"
below). The only things left are steps that need your real Neon account and can't be
done from here: creating the actual database and pointing the app at it.

## What's already in the project

| File | What it does |
|---|---|
| `lib/db.ts` | Neon HTTP driver + Drizzle client |
| `lib/db-schema.ts` | Auth tables (`user`, `session`, `account`, `verification`) — auto-generated by the Better Auth CLI |
| `drizzle.config.ts` | Drizzle Kit config, points at `DATABASE_URL` |
| `drizzle/0000_skinny_supernaut.sql` | The migration that creates those 4 tables — ready to run |
| `lib/auth.ts` | Better Auth server instance (email/password enabled) |
| `app/api/auth/[...all]/route.ts` | Auth API — sign-up, sign-in, sign-out, sessions |
| `lib/auth-client.ts` | `useSession`, `signIn`, `signUp`, `signOut` for client components |
| `app/sign-in/page.tsx`, `app/sign-up/page.tsx` | Real auth pages, styled to match your glass design system |
| `app/dashboard/page.tsx` | Placeholder authenticated landing page (shows the signed-in user, a Sign Out button) |
| `proxy.ts` | Route protection for `/dashboard/*` — **note:** this is `proxy.ts`, not `middleware.ts`. Next.js 16 renamed the convention; a leftover `middleware.ts` is silently ignored, so this rename matters. |
| `components/Header.tsx` | "Sign In" now goes to `/sign-in` (the old `/admin/login` link was dead — that route never existed in your project); shows Dashboard/Sign Out once logged in |
| `.env.local` | Has a **real** generated `BETTER_AUTH_SECRET` already — you only need to fill in `DATABASE_URL` |
| `.env.example` | Committable reference for the above |
| `package.json` / `pnpm-lock.yaml` | `better-auth`, `drizzle-orm`, `@neondatabase/serverless`, `drizzle-kit` added |

**Important — I did *not* gate `/landlord`.** That page is your public "Submit Your
Property" WhatsApp lead-gen form, not a dashboard. Locking it behind sign-in would
have broken that public flow, so I built a separate `/dashboard` route for
authenticated users instead and pointed `proxy.ts` at that.

## What you need to do

### 1. Create the Neon database (5 min)

1. Go to [console.neon.tech](https://console.neon.tech) → **New Project** → name it
   `platinum-rentals`.
2. Open **Connection Details** and copy the **pooled** connection string (it has
   `-pooler` in the hostname).

### 2. Paste it into `.env.local`

Open `.env.local` in the project root and replace the placeholder:

```bash
DATABASE_URL="postgresql://your-real-pooled-connection-string"
```

Leave `BETTER_AUTH_SECRET` as-is — a real one was already generated for you. If you
ever suspect it's leaked, regenerate with `openssl rand -base64 32`.

### 3. Apply the migration

The SQL that creates the `user`, `session`, `account`, and `verification` tables is
already written and sitting in `drizzle/0000_skinny_supernaut.sql`. Run:

```bash
npx drizzle-kit migrate
```

This applies it to your real Neon database. Check the Neon console's **Tables** tab
afterward — you should see all four tables.

*(If you change `lib/db-schema.ts` later — e.g. adding a `properties` table — run
`npx drizzle-kit generate` to create a new migration file, then `npx drizzle-kit
migrate` again.)*

### 4. Install and run

```bash
pnpm install
pnpm dev
```

Visit `http://localhost:3000/sign-up`, create an account, and confirm:
- You're redirected to `/dashboard`
- The header now shows "Dashboard" / "Sign Out" instead of "Sign In"
- Signing out returns you to `/sign-in`
- Visiting `/dashboard` in an incognito window (no session) redirects you to `/sign-in`

### 5. Before deploying

In your host's environment variables (e.g. Vercel → Project Settings → Environment
Variables), set the same four keys, but with production values:

```bash
DATABASE_URL=<same Neon pooled string>
BETTER_AUTH_SECRET=<same secret, or a new one generated the same way>
BETTER_AUTH_URL=https://your-real-domain.ug
NEXT_PUBLIC_APP_URL=https://your-real-domain.ug
```

`BETTER_AUTH_URL` and `NEXT_PUBLIC_APP_URL` must be `localhost` in dev and your real
domain in production — get this wrong and sign-in will silently fail with a cookie/
origin mismatch.

## Optional next step: move property listings into Neon

`lib/data.ts` still exports a static `SAMPLE_PROPERTIES` array — that's untouched and
still works exactly as before. Auth and property data are independent right now.
When you're ready to connect them (so a landlord's dashboard can show "your
listings"), that's a separate, bigger piece of work:

1. Add a `properties` table to `lib/db-schema.ts` with a `landlordId` column
   referencing `user.id`.
2. `npx drizzle-kit generate` then `npx drizzle-kit migrate`.
3. Seed it from `SAMPLE_PROPERTIES`.
4. Swap the functions in `lib/data.ts` (`getPropertyById`, `getSimilarProperties`,
   etc.) to query the database, keeping the same names/signatures so none of your
   page components need to change.

Just ask when you're ready and I'll implement that too.

## What was verified here (before packaging)

- `npx tsc --noEmit` — passes, zero errors
- `npx next build` — traces successfully through every new file (`proxy.ts`, the auth
  API route, `lib/auth.ts`, `lib/db.ts`, sign-in/sign-up/dashboard pages, the updated
  `Header.tsx`). The build only stops at the font-loading step, which fails here
  because this sandbox can't reach `fonts.googleapis.com` — that's an environment
  restriction, not a bug in the code, and it will build fine wherever you normally
  deploy.
- `npx @better-auth/cli generate` — ran successfully and produced the schema in
  `lib/db-schema.ts`
- `npx drizzle-kit generate` — ran successfully and produced
  `drizzle/0000_skinny_supernaut.sql`

I could not run `drizzle-kit migrate` against a real database or actually create a
Neon project, since that requires your account and isn't reachable from this
environment — that's the one manual step above (#3).
